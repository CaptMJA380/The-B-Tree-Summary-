§ I · The Problem That Started It All
01 · Origin

Why the B-Tree Had to Be Invented

In the late 1960s, computers were increasingly being tasked with managing enormous volumes of data — payroll records, airline reservations, inventory systems. But the hardware of the era imposed a brutal constraint: memory was tiny and expensive, and the only way to hold large datasets was on magnetic disk drives.

Disk drives were orders of magnitude slower than memory. Every time a program needed to look something up, it had to perform a disk read — a mechanical operation taking milliseconds, whereas a memory operation took nanoseconds. With millions of records, even a simple search could require dozens of disk accesses, each one painfully slow.

The existing solutions — simple sorted arrays, binary search trees, hash tables — were designed with fast, random-access memory in mind. They were fundamentally mismatched with disk I/O patterns. Rudolf Bayer and Edward McCreight at Boeing Scientific Research Laboratories recognized this mismatch and set out to design a structure from first principles around the economics of disk storage.

"The problem of organizing large files in external storage has become increasingly important. The paging concept forms the basis of most modern operating systems but the efficient organization of large stored sets remains open."
— Bayer & McCreight, Acta Informatica, 1972
§ II · The Architecture of the B-Tree
02 · The Concept

How the B-Tree Actually Works

The B-Tree is a self-balancing tree data structure that maintains sorted data and allows searches, insertions, deletions, and sequential access in logarithmic time. Unlike a binary tree where each node holds one key and has at most two children, a B-Tree node can hold many keys and have many children.

The "B" in B-Tree is intentionally ambiguous — Bayer himself said it could stand for Balanced, Broad, Bushy, or simply Bayer. The key insight is that a B-Tree of order m ensures:

⌈m/2⌉ Minimum children per internal node
m Maximum children per node (the "order")
O(log n) Guaranteed time for search, insert, delete

The genius is in what this achieves: by packing many keys into one node, a single disk read (which retrieves a whole block/page) can load an entire node. A B-Tree of order 1,000 can index a billion records in just three disk reads. That's the insight that changed everything.

Core Properties

All leaves at the same depth. The tree is perfectly height-balanced — every path from the root to a leaf has the same length. This guarantees worst-case performance is the same as average-case.

Nodes are always at least half full. Every node (except the root) must contain at least ⌈m/2⌉ − 1 keys. This ensures the tree remains "bushy" and the height stays logarithmic.

Splits propagate upward. When a node becomes too full during an insertion, it splits in two and the median key is pushed up to the parent. This is how the tree grows — only from the root, which is why it stays balanced.

§ III · The World Before & After
03 · Before & After

A World Transformed

The emergence of the B-Tree did not merely improve an existing system — it fundamentally altered what was computationally achievable. Here is the world on either side of 1972.

Before the B-Tree · Pre-1972

  • Sequential file scans were the norm — finding a record meant reading from the beginning of a file until it was found
  • Binary search trees degenerated to linked lists on sorted input, requiring expensive periodic rebalancing
  • ISAM (Indexed Sequential Access Method) files required manual cylinder/track indexes and suffered from overflow chains
  • Database "indexes" were often hand-crafted, application-specific structures rebuilt nightly in batch jobs
  • A query over 1 million records could require hundreds of disk reads and take minutes
  • Insertions into sorted structures required rewriting large swaths of disk storage
  • No general-purpose solution existed — every system reinvented its own ad-hoc indexing

After the B-Tree · Post-1972

  • Any sorted dataset of any size could be searched in O(log n) disk reads — predictable, guaranteed performance
  • IBM's System R (1974) and other relational databases adopted B-Trees immediately as their primary index structure
  • Insertions and deletions became self-managing — no manual rebalancing, no batch rebuilds
  • Range queries became efficient — once the start point was found, sequential scans along leaf nodes required no backtracking
  • A billion-record database could be searched in 3–4 disk reads with a B-Tree of sufficient order
  • Oracle, MySQL, PostgreSQL, SQLite, MongoDB (WiredTiger), InnoDB — all use B-Trees or B+ Trees as their core
  • File systems (NTFS, HFS+, ext4, APFS) adopted B-Trees for directory indexing

§ V · Revolutionary Impact
05 · Impact

A Structure That Outlasted Its Era

Few data structures have enjoyed the longevity and universality of the B-Tree. Published over fifty years ago, it not only solved the problem it was designed for but proved so elegantly general that it became the substrate upon which the modern information economy is built.

1972
The Paper is Published

Bayer & McCreight publish "Organization and Maintenance of Large Ordered Indexes" in Acta Informatica. The paper introduces the B-Tree and its balancing invariants.

1973–1974
The B+ Tree Variant

Douglas Comer and others develop the B+ Tree, where all data is stored in leaf nodes connected as a linked list, dramatically improving range scans. This becomes the dominant variant in databases.

1979
Oracle Version 2 Launches

The first commercially available SQL database ships with B-Tree indexes at its core, establishing the pattern every relational database would follow for decades.

1993
NTFS Adopts B+ Trees

Microsoft's NTFS file system uses B+ Trees for its Master File Table, allowing hundreds of thousands of files to be indexed and found in milliseconds.

2000s
Web-Scale Databases

MySQL's InnoDB engine (now default), PostgreSQL, and SQLite all use B+ Trees. As web applications explode in scale, B-Trees silently handle billions of queries per day.

2010s–Present
SSD Era & New Variants

SSDs change the I/O landscape, but B-Trees remain dominant. New variants like the Bε-Tree and fractal tree indexes emerge, all descended from the original 1972 paper. Apple's APFS, introduced in 2017, uses a B-Tree variant for its on-disk format.

"The B-tree is one of the most used data structures in computer science. Almost every database management system, file system, and key-value store uses a B-tree or one of its variants as the primary indexing structure."
— Widely attributed across database literature

Why It Has Never Been Dethroned

The B-Tree's longevity comes from a rare combination of properties that no competing structure has been able to fully replicate: it provides guaranteed worst-case logarithmic performance, it is self-managing (no external rebalancing), it maps naturally onto block-based storage (disk, SSD, memory pages), it supports both exact-match and range queries efficiently, and it degrades gracefully under concurrent access. Hash tables are faster for point lookups but cannot do range queries. LSM-Trees (used in LevelDB, RocksDB, Cassandra) write faster but read slower. Skip lists are simpler but space-inefficient. The B-Tree remains the general-purpose champion.
